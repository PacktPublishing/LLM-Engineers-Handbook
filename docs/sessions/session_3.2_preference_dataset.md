## 🏗️ Architecture Overview

### Instruction vs Preference Data

```
Instruction dataset (Session 3.1)          Preference dataset (this session)
┌──────────────────────────────┐           ┌──────────────────────────────┐
│ instruction                  │           │ instruction                  │
│ answer                       │           │ chosen     (good, from text) │
└──────────────────────────────┘           │ rejected   (model-generated) │
   "Here is the right answer"              └──────────────────────────────┘
                                                    ▲             ▲
                                            verbatim from   plausible but
                                            the source      imperfect
```

Instruction tuning teaches the model **to answer**. Preference tuning teaches it **which answer is better** by contrasting a high-quality reference against a plausible but weaker generation.

### Generation Flow

```
query_feature_store(after=...) ──► create_prompts(dataset_type=PREFERENCE)
        │
        ▼
PreferenceDatasetGenerator.generate()
        │  ChatOpenAI(temp=0.7, max_tokens=2000)
        │  → 5 triples per extract (instruction, rejected, chosen)
        ▼
post_process_datasets()
        │  filter_short_answers(min_length=100)
        │  filter_answer_format()  (capital start, terminal . ! ?)
        ▼
create_preference_train_test_split(random_state=42)
        │
        ▼
PreferenceTrainTestSplit
        │
        ▼  (optional)
push_to_huggingface  →  prompt / rejected / chosen
```

### The asymmetry at the heart of this dataset

Most preference datasets pair two *model-generated* answers, then ask a judge which is better. This project does something different and simpler:

| Role | Source | Guarantee |
|------|--------|-----------|
| `chosen` | A verbatim excerpt from the cleaned corpus | Authentic style and facts by construction |
| `rejected` | Generated by GPT-4o-mini "based on the context" | Fluent but not guaranteed faithful or on-style |

Because `chosen` is extracted, the project **skips the expensive evaluation stage** entirely. There is a ground-truth answer in the text, so no LLM judge, no reward model, no human rating is needed. This is the single most important design decision of the session.

## 🧠 DPO in One Page

DPO replaces a separate reward model with a direct loss over preference pairs.

For each triple `(prompt x, chosen y_w, rejected y_l)`:

```
L_DPO = - log σ( β · [ log πθ(y_w | x) - log πref(y_w | x)
                       - ( log πθ(y_l | x) - log πref(y_l | x) ) ] )
```

- **`πθ`** is the model being trained; **`πref`** is a frozen reference (usually the SFT checkpoint).
- The inner term compares how much *more* likely the policy makes the chosen answer versus the rejected one, relative to the reference.
- **`β`** controls how far the policy may drift from the reference (a KL-style regularizer). The book states the popular value is **0.1**; at `β=0` the reference is ignored entirely (p. 277).
- The SFT/instruction stage (Session 3.1 / 5.1) is the usual reference point, which is why this pipeline produces **both** dataset types.

### Why the `chosen` answer must be verbatim

DPO assumes `chosen` is genuinely better. A re-written "good answer" can drift from the source's style and facts. This dataset's chosen answer is an exact excerpt from the corpus, guaranteeing a high-quality, on-style target. The book's stated goal (p. 266) is to make the model *less artificial and more authentic* — copies the casual voice of the blog articles.

### DPO vs RLHF in one table

| Aspect | RLHF + PPO | DPO |
|--------|-----------|-----|
| Reward model | separate, trained | implicit (closed-form) |
| RL algorithm | PPO | none — binary cross-entropy |
| Sampling during training | required | not required |
| Stability | sensitive to hyperparameters | more stable |
| Peak performance at scale | higher ceiling (millions of pairs) | close, cheaper |
| Reference model | frozen | frozen (β controls distance) |

The book's verdict (p. 279): for most applications DPO gives the majority of the benefit at lower engineering cost; PPO-inspired methods still win at very large scale.

## 📚 Theory: Preference Data (Book Chapter 6, pp. 258-274)

### Format and standardization

Preference datasets have **no standard storage format** (unlike Alpaca/ShareGPT for instructions), because different algorithms need different shapes. For DPO the shape is simple: one instruction, one preferred answer, one rejected answer.

| Instruction | Chosen answer | Rejected answer |
|-------------|---------------|-----------------|
| Tell me a joke about octopuses. | Why don't octopuses play cards in casinos? Because they can't count past eight. | How many tickles does it take to make an octopus laugh? Ten tickles. |

Multi-turn conversations are uncommon; major fine-tuning libraries typically extract only the first or last message.

**Why the rejected answer matters as much as the chosen one**: without it, the dataset collapses to a plain instruction set. The rejected response encodes the behavior to *eliminate*.

### When preference data beats SFT alone

The book lists the domains where preference data wins because quality is subjective:

- **Chatbots** — naturalness, engagement, contextual appropriateness
- **Content moderation** — nuanced borderline judgments
- **Summarization** — conciseness, relevance, coherence
- **Code generation** — efficiency, readability, best practice among correct solutions
- **Creative writing** — style, creativity, emotional impact
- **Translation** — fluency/naturalness beyond BLEU

### Data quantity

| Scope | Typical pairs | Note |
|-------|---------------|------|
| General-purpose alignment | millions | Nvidia, Meta multi-round pipelines |
| Open-source community | 10,000 - 100,000 | also heals networks after merge/prune |
| Task-specific alignment | 100 - 10,000 | e.g. style change, refusal behavior |
| Very small task (e.g. "not trained by OpenAI") | 200 - 500 | rejected = wrong-origin claims |

DPO is generally **less destructive than SFT** and has a milder impact on the final model. The project's run yields **2,970 triples**, filtered to **1,467** (p. 274) — squarely in the task-specific range, which matches the goal of changing writing style.

### The four generation strategies (quality/cost/scale tradeoffs)

| Generation | Evaluation | Quality | Cost | Scale | Real-world use |
|------------|------------|---------|------|-------|----------------|
| Human | Human | highest | extreme | tiny | big AI labs |
| Human | LLM | mixed | high (human writing) | small | rare |
| LLM | Human | good | medium | medium | preferred when human judgment matters |
| LLM | LLM (synthetic) | variable | low | huge | increasingly common |

The book's practical guidance: humans are better at *judging* answers than writing them, so **LLM-generated + human-evaluated** offers a good balance. Fully synthetic datasets scale best but need careful prompt engineering and can perpetuate the generator's biases.

**A shortcut the book highlights**: evaluation is not always required because preferences can emerge from the generation process. Use a strong model for the preferred output and a weaker/flawed model for the alternative (the Intel `orca_dpo_pairs` dataset does this). The LLM Twin takes the extreme version: the "strong" side is the human-written corpus itself.

### Evaluation methods and their biases

LLM evaluation is either **absolute scoring** (rate 1-5) or **pairwise ranking** (which of A/B is better). Pairwise ranking is preferred for preference data because it mirrors how humans compare and correlates better with human judgment. Quality improves with a **ground-truth answer** and **chain-of-thought** reasoning; with no ground truth, ask the judge to write a **grading note** first.

Three biases to know and mitigate:

| Bias | Description | Mitigation |
|------|-------------|------------|
| Position | judge favors the first answer | randomize A/B order |
| Length | judge favors longer answers | length normalization; balanced few-shot examples |
| Family | judge favors its own model family | use a jury of multiple models |

## 📁 Key Files Explained

### 1. `PreferenceDatasetGenerator` - The Prompt

```python
# llm_engineering/application/dataset/generation.py
class PreferenceDatasetGenerator(DatasetGenerator):
    dataset_type = DatasetType.PREFERENCE

    prompt_template_str = """Based on the following extract, generate five instruction-answer triples. Each triple should consist of:
1. An instruction asking about a specific topic in the context.
2. A generated answer that attempts to answer the instruction based on the context, named as 'rejected'.
3. An extracted answer that is a relevant excerpt directly from the given context, named as 'chosen'.

Instructions must be self-contained and general, without explicitly mentioning a context, system, course, or extract.

Important:
- Ensure that the extracted answer, the chosen one, is a verbatim copy from the context, including all punctuation and apostrophes.
- Do not add any ellipsis (...) or [...]  to indicate skipped text in the extracted answer.
- If the relevant text is not continuous, use two separate sentences from the context instead of skipping text.

Structure the answer in JSON format, ready to be loaded in Python by json.loads(), as a list of objects.
Do not add any extra characters and provide your response in JSON format with the following structure:
[
    {
        "instruction": "...",
        "rejected": "...",
        "chosen": "..."
    },
    ...
]

Extract:
{{extract}}
"""
```

**Prompt-design principles**:
- **`rejected` is model-generated** ("attempts to answer... based on the context"): plausibly fluent but not guaranteed faithful.
- **`chosen` is extracted from the context**: verbatim, so it inherits the author's style and facts.
- **Verbatim rules** ("including all punctuation and apostrophes", "no ellipsis") exist so the chosen string is a true quotation, not a summary.
- **The discontiguous-rule** ("use two separate sentences instead of skipping text") prevents fabricated continuity.

> ⚠️ Note: the step function is named `generate_preference_dataset` (correct spelling), but the instruction step is misspelled `generate_intruction_dataset`. The enum is `DatasetType.PREFERENCE` — always use the enum, not a string literal.

#### Book names vs repo names (do not conflate)

The book's standalone script uses different key names than the repo. Both describe the same triple:

| Role | Book (p. 270) | Repo / HF schema |
|------|---------------|------------------|
| The task text | `instruction` | `instruction` (exported as `prompt`) |
| The model-generated answer | `generated_answer` | `rejected` |
| The verbatim answer | `extracted_answer` | `chosen` |
| JSON wrapper key | `"preference_triples"` | bare array |
| Python container class | `PreferenceSet` | `PreferenceDatasetSample` |

The book's `PreferenceSet`:

```python
class PreferenceSet:
    def __init__(self, triples):
        self.triples = triples

    @classmethod
    def from_json(cls, json_str: str) -> "PreferenceSet":
        data = json.loads(json_str)
        triples = [(t["instruction"], t["generated_answer"], t["extracted_answer"])
                   for t in data["preference_triples"]]
        return cls(triples)

    def __iter__(self):
        return iter(self.triples)
```

The repo's `ListPydanticOutputParser` instead validates a bare array of `{instruction, rejected, chosen}` objects. When reading the book, translate `generated_answer` → `rejected` and `extracted_answer` → `chosen`.

### 2. Post-Processing: The Two Filters

```python
# llm_engineering/application/dataset/generation.py
    @classmethod
    def post_process_datasets(
        cls, datasets: dict[DataCategory, domain.dataset.PreferenceDataset], test_size: float
    ) -> TrainTestSplit:
        datasets = generation_utils.filter_short_answers(datasets)
        datasets = generation_utils.filter_answer_format(datasets)

        remaining_samples = sum([dataset.num_samples for dataset in datasets.values()])
        logger.info(
            f"Filtered out short answers and answers with incorrect format. Remaining samples: {remaining_samples}"
        )

        train_test_split = generation_utils.create_preference_train_test_split(
            datasets, test_size=test_size, random_state=42
        )
        return train_test_split
```

**Filter 1 - minimum length**:

```python
def filter_short_answers(
    data: dict[DataCategory, PreferenceDataset], min_length: int = 100
) -> dict[DataCategory, PreferenceDataset]:
    def is_long_enough(example: PreferenceDatasetSample) -> bool:
        return len(example.chosen) >= min_length

    filtered_data = {}
    for category, dataset in data.items():
        filetered_dataset_samples = list(filter(is_long_enough, dataset.samples))
        filtered_dataset = PreferenceDataset(category=category, samples=filetered_dataset_samples)

        filtered_data[category] = filtered_dataset

    return filtered_data
```

**Filter 2 - answer shape**:

```python
def filter_answer_format(data: dict[DataCategory, PreferenceDataset]) -> dict[DataCategory, PreferenceDataset]:
    def is_valid_format(example: PreferenceDatasetSample) -> bool:
        chosen = example.chosen

        return len(chosen) > 0 and chosen[0].isupper() and chosen[-1] in (".", "!", "?")

    filtered_data = {}
    for category, dataset in data.items():
        filetered_dataset_samples = list(filter(is_valid_format, dataset.samples))
        filtered_dataset = PreferenceDataset(category=category, samples=filetered_dataset_samples)

        filtered_data[category] = filtered_dataset

    return filtered_data
```

**Key Concepts**:
- **Length filter (>= 100 chars on `chosen`)**: a one-line chosen answer carries almost no signal for DPO; the contrast between chosen and rejected would be trivial.
- **Format filter (capital start, terminal punctuation)**: enforces that `chosen` is a real sentence, not a fragment.
- **Both filters drop whole samples**, never edit them. Editing a verbatim quotation would break the "chosen is authentic" guarantee.
- **Filters run before the split**, so the test set is also clean.
- The internal typo `filetered_dataset_samples` is harmless; it is a local variable.

#### Why these two filters and not more

The book (p. 272) frames both as **heuristics** to remove poor-quality samples, and the stated outcome is heavy: 2,970 raw triples -> **1,467** retained (p. 274). Roughly half the data is dropped. That is expected, not a bug:

| Filter | Removes | Rationale |
|--------|---------|-----------|
| `filter_short_answers` | answers < 100 chars | too little text for a meaningful preference contrast |
| `filter_answer_format` | fragments, lowercase starts, missing punctuation | not a complete sentence, so not a clean verbatim target |

Because `chosen` is a verbatim extract, a fragment likely means the chunking or extraction step mis-fired. Dropping it is cheaper than repairing it.

**Edge case**: a valid but short chosen answer (say 90 chars that is a complete sentence) is dropped by the length filter. If your corpus is terse, lower `min_length`. Conversely, raising it too high can empty a small category.

### 3. The Schema and Hugging Face Export

```python
# llm_engineering/domain/dataset.py
class PreferenceDatasetSample(VectorBaseDocument):
    instruction: str
    rejected: str
    chosen: str

    class Config:
        category = DataCategory.PREFERENCE_DATASET_SAMPLES


class PreferenceDataset(VectorBaseDocument):
    category: DataCategory
    samples: list[PreferenceDatasetSample]

    class Config:
        category = DataCategory.PREFERENCE_DATASET

    @property
    def num_samples(self) -> int:
        return len(self.samples)

    def to_huggingface(self) -> "Dataset":
        data = [sample.model_dump() for sample in self.samples]
        return Dataset.from_dict(
            {
                "prompt": [d["instruction"] for d in data],
                "rejected": [d["rejected"] for d in data],
                "chosen": [d["chosen"] for d in data],
            }
        )
```

**Key Concepts**:
- **Column remap on export**: internal `instruction` becomes the Hugging Face `prompt` column. This is exactly the schema `trl`'s DPO trainer expects.
- **`chosen` / `rejected` names are not arbitrary** — they are the reserved names in the TRL DPO data collator.
- The generation `max_tokens=2000` (vs 1200 for pairs) is set in the base `generate()` because triples are longer.

#### Schema mapping table

```
PreferenceDatasetSample        Hugging Face Dataset
{instruction, rejected, chosen}  ───►  {prompt, rejected, chosen}
```

### 4. Splitting

```python
def create_preference_train_test_split(
    data: dict[DataCategory, PreferenceDataset], test_size=0.2, random_state=42
) -> PreferenceTrainTestSplit:
    train_data = {}
    test_data = {}

    for category, dataset in data.items():
        samples = dataset.samples
        samples_dicts = [sample.model_dump() for sample in samples]

        if len(samples_dicts) > 0:
            train_samples_dicts, test_samples_dicts = train_test_split(
                samples_dicts, test_size=test_size, random_state=random_state
            )
            train_samples = [PreferenceDatasetSample(**sample_dict) for sample_dict in train_samples_dicts]
            test_samples = [PreferenceDatasetSample(**sample_dict) for sample_dict in test_samples_dicts]
        else:
            train_samples = []
            test_samples = []

        train_dataset = PreferenceDataset(category=category, samples=train_samples)
        test_dataset = PreferenceDataset(category=category, samples=test_samples)

        train_data[category] = train_dataset
        test_data[category] = test_dataset

    return PreferenceTrainTestSplit(train=train_data, test=test_data, test_split_size=test_size)
```

Mirrors the instruction splitter: per category, seed 42, empty-safe.

#### The configured test size

The instruction config uses `test_split_size: 0.1`; the preference config uses `test_split_size: 0.05`. The preference split is smaller because the filtered dataset (~1,467) is already small and preference pairs are expensive to produce; keeping more in train maximizes the signal for DPO.

### 6. The Shared Base Makes This Small

Preference and instruction generation share almost everything. The only differences:

| Aspect | Instruction | Preference |
|--------|-------------|------------|
| `dataset_type` | `INSTRUCTION` | `PREFERENCE` |
| System prompt slot | "instruction-answer pairs" | "instruction-answer triples" |
| Prompt template | pairs | triples |
| Sample Pydantic type | `InstructDatasetSample` | `PreferenceDatasetSample` |
| `max_tokens` | 1200 | 2000 |
| `post_process_datasets` | split only | filter + split |
| HF columns | `instruction`, `output` | `prompt`, `rejected`, `chosen` |

Everything else — tokenizer, truncation, batching, parser, error handling, splitting seed — is inherited. This is the payoff of the template-method base class.

## 🔬 Worked Example: One Triple Through Both Filter Paths

Take one raw triple from `generate()`:

```json
{"instruction": "Explain why a feature store prevents training-serving skew.",
 "rejected": "A feature store stores features. It is useful for machine learning.",
 "chosen": "Without a feature store, training and serving drift apart, and the model sees different data than it was trained on."}
```

**Trace**:

1. `filter_short_answers` measures `len(chosen)`. Here `chosen` is ~104 chars -> passes.
2. `filter_answer_format` checks `chosen[0].isupper()` -> `"W"` is uppercase; `chosen[-1] in (".", "!", "?")` -> `"."` -> passes.
3. The triple survives and enters the split.

Now take the mock triple #3 from `constants.py`:

```json
{"instruction": "<mocked generated instruction> 3",
 "rejected": "<mocked generated answer> 3",
 "chosen": "Mocked extracted answer 3"}
```

`filter_short_answers`: `len("Mocked extracted answer 3") == 25 < 100` -> **dropped**.

Now take a fragment:

```json
{"chosen": "a feature store sits between the pipeline and the model"}
```

`filter_answer_format`: `chosen[0] == "a"` is not uppercase -> **dropped**.

This is exactly why the mocked preference response in `constants.py` has two long `chosen` values (pass) and one short one (fail): the mock is engineered to exercise both filter outcomes in CI.

### Task

```python
def spans_of(chosen: str, source: str) -> int:
    # count maximal contiguous appearances (approximate)
    idx = source.find(chosen)
    if idx != -1:
        return 1
    # split on sentence boundary and check both halves
    import re
    parts = [p for p in re.split(r"(?<=[.!?])\s+", chosen) if p.strip()]
    found = sum(1 for p in parts if p in source)
    return found if found else 0
```

## 🐛 Common Pitfalls

- **`chosen` not verbatim**: if the model paraphrases, DPO learns the wrong target. The verbatim rules in the prompt plus the format filter guard this, but always spot-check real runs.
- **Too few samples after filtering**: aggressive filters can empty a small category. The book's real run keeps only ~49%. The pipeline logs the remaining count, but a silent empty train set will fail later at training time.
- **Category mismatch**: use `DatasetType.PREFERENCE` (the enum). Typos in the dataset-type string raise `ValueError` inside `get_dataset_generator`.
- **Conflating book and repo names**: `generated_answer`/`extracted_answer` (book) are `rejected`/`chosen` (repo/HF). Mixing them breaks the DPO collator, which reserves `chosen`/`rejected`/`prompt`.
- **Treating the mock's filter drop as a bug**: the third mock triple is *designed* to fail so CI exercises the filter path.
- **`beta` confusion**: this session builds the data; `beta` is a DPO trainer setting (0.1 is the book's recommended default). Do not put it in the dataset.
- **Multi-turn assumption**: do not build multi-turn preference data — major trainers extract only the first/last message.
- **Missing verbatim check in production**: the pipeline does not automatically verify `chosen in source`. Add a post-generation assertion for real runs.
- **Ignoring verbosity drift**: the book warns DPO tends to make models more verbose and formal; too many long `chosen` extracts can amplify this.

## 🎓 Knowledge Check

1. **In DPO, which answer is model-generated and which is from the corpus?**
   - `rejected` is model-generated; `chosen` is a verbatim excerpt from the context.

2. **Why must `chosen` be verbatim?**
   - DPO assumes chosen is genuinely better; a paraphrase could drift from the source's facts and style.

3. **What does `filter_short_answers` protect against?**
   - Trivially short chosen answers that give almost no preference signal.

4. **What does `filter_answer_format` check?**
   - Chosen starts with a capital and ends with `.`, `!`, or `?`.

5. **What are the Hugging Face DPO column names, and what do they map from?**
   - `prompt`/`chosen`/`rejected`, mapped from `instruction`/`chosen`/`rejected`.

6. **Why is SFT a prerequisite for DPO in this project?**
   - The DPO reference policy is the SFT checkpoint; without it, there is no sensible `πref`.

7. **Why does this project skip the LLM-judge evaluation stage?**
   - The chosen answer is a ground-truth excerpt from the corpus, so no judge is needed to establish which answer is better.

8. **What is the book's recommended `beta` value, and what does `beta=0` mean?**
   - 0.1; at `beta=0` the reference model is ignored, so the policy can drift far from the SFT model.

9. **Name the four preference-generation strategies.**
   - Human-generated/human-evaluated, human-generated/LLM-evaluated, LLM-generated/human-evaluated, LLM-generated/LLM-evaluated.

10. **Why is pairwise ranking preferred over absolute scoring for preference data?**
    - It mirrors how humans compare and correlates better with human judgment.

11. **Name the three LLM-judge biases and one mitigation each.**
    - Position (randomize order), length (length normalization / balanced few-shot), family (jury of models).

12. **Why are the filters applied before the train/test split?**
    - So the test split is also clean and evaluation is not skewed by bad samples.

13. **What is the configured `test_split_size` for preference vs instruction, and why?**
    - 0.05 vs 0.1; the preference set is smaller and pairs are expensive, so more stays in train.

14. **How do the book's `generated_answer`/`extracted_answer` map to the repo?**
    - They map to `rejected`/`chosen`.

15. **What does the project's real filter retention (~49%) tell you?**
    - It is expected; the two heuristics are intentionally aggressive to guarantee clean verbatim targets.

## 📖 Glossary

- **Chosen** — the preferred answer; here, a verbatim excerpt from the corpus.
- **Rejected** — the dispreferred answer; here, generated by the model.
- **DPO** — Direct Preference Optimization; closed-form preference alignment without a reward model.
- **β (beta)** — DPO's KL-regularization strength; controls distance from the reference policy.
- **πθ / πref** — the policy being trained and the frozen reference policy.
- **Pairwise ranking** — judging by comparing two answers rather than scoring one.
- **Verbatim** — copied exactly, including punctuation and apostrophes, with no ellipses.
- **PreferenceSet** — the book's standalone container for triples (`instruction`, `generated_answer`, `extracted_answer`).
- **TRL** — Transformers Reinforcement Learning library; provides `DPOTrainer` and the reserved `prompt`/`chosen`/`rejected` columns.
